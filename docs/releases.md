# Ветки и опубликованные версии

`main` содержит актуальную выпущенную линию 3+, сейчас Petrovich 3.0.0.
Точная ревизия опубликованного пакета — тег `v3.0.0`. Уточнения документации
после релиза не изменяют этот тег и не означают новый выпуск в PyPI.
Следующая версия готовится в `develop`; завершённые release-ветки удаляются
после слияния. Исторические `master`, `petrovich_2`, `release/3.0` и `legacy/1.x`
заменены этой схемой. Их коммиты сохранены в истории `main`.

## Замороженные выпуски

Каждому старому выпуску соответствует отдельная неподдерживаемая ветка и тег:

- PyPI `0.1` → `legacy/0.1` → `v0.1`.
- PyPI `0.1.1` → `legacy/0.1.1` → `v0.1.1`.
- PyPI `0.1.3` → `legacy/0.1.3` → `v0.1.3`.
- PyPI `1.0.0` → `legacy/1.0.0` → `v1.0.0`.
- PyPI `2.0.1` → `legacy/2.0.1` → `v2.0.1`.
- PyPI `3.0.0` → история `main` → `v3.0.0`.

Legacy-ветки созданы из опубликованных дистрибутивов, а не из предположительно
близких коммитов. Каждый файл сохранён побайтово; у sdist снят только внешний
каталог архива. Служебные метаданные упаковки также сохранены. Дополнительно
добавлены `ARCHIVE.md` и `ARCHIVE.json` с происхождением, SHA-256 дистрибутива
и контрольными суммами всех его файлов. Сводный машиночитаемый реестр:
[legacy-releases.json](legacy-releases.json).

Для 2.0.1 в PyPI доступен только wheel. Его снимок сохраняет опубликованный
Python-код и данные, но не восстанавливает отсутствующие setup.py, CI или
историю оригинальной сборки. Установка старых версий выполняется из PyPI,
например `python -m pip install Petrovich==2.0.1`.

Архивные дефекты не исправляются: например, отсутствие правил в дистрибутиве
0.1 сохраняется как часть истории. Legacy не проходит современный CI,
не сопровождается и не публикуется заново. Защитите `legacy/*` от обновления
и удаления правилами репозитория; ветки нужны для чтения и воспроизведения истории.

## Исторические теги

Ранее существовавшие теги без префикса `v` (`0.1`, `0.1.1`, `0.1.5`, `1.0.0`)
не удаляются и не перемещаются. Это ссылки на прежнюю Git-историю. Для точных
снимков PyPI используйте перечисленные выше теги с префиксом `v`.
Тег `0.1.5` не имеет соответствующего доступного релиза в PyPI на момент сверки
12 октября 2026 года. Версия `2.0.0` также не представлена в текущем реестре PyPI;
для них не создаются фиктивные теги опубликованных выпусков.

## Правила релизов

Новый релиз 3+ готовится из `develop` в `release/MAJOR.MINOR`. После проверок
версия в `pyproject.toml` должна точно совпадать с тегом `vMAJOR.MINOR.PATCH`.
Публикация выполняется GitHub Actions через Trusted Publishing. После успеха
изменения вливаются в `main` и обратно в `develop`. Уже опубликованные теги
не передвигают: любые изменения пакета требуют новой версии.
